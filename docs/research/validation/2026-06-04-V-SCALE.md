# V-SCALE — Scoring Comparability Validation
**C0a/C0b: Is ACF-sweep 53.1% Acc2 directly comparable to firmware 40.6% Acc2?**
**Adversarial default: NOT VERIFIED. Override only with reproducible evidence.**

---

## 1. What the claim asserts

The claim under attack states the 53.1% figure (from `acf_ceiling_sweep.py`) and the 40.6% figure
(from `tempo_accuracy.py`) are scored identically, making their ~12pp difference a valid "gap to close"
for the firmware's winner-selection.

---

## 2. Scoring machinery — line-by-line comparison

### 2.1 Ground-truth source and corpus/GT track mapping

Both scripts use **identical GT machinery**:

- `tempo_accuracy.py` defines `load_gt()`, `DEFAULT_CORPUS`, `DEFAULT_GT` — HarmonixSet gold human
  BPM annotations, joined `youtube_id → file_key → metadata.csv BPM`.
- `acf_ceiling_sweep.py` REUSE CONTRACT (lines 27): `"GT load + corpus/GT defaults: imported from
  tempo_accuracy (load_gt, DEFAULT_*)"`.

**Verdict on GT/corpus mapping: IDENTICAL.** Same 36-track HarmonixSet corpus, same `metadata.csv`
BPM column, same `youtube_id → file_key` join.

### 2.2 In-range filter

Both use `BPM_LO <= g["bpm"] <= BPM_HI` (60–155 BPM). `acf_ceiling_sweep.py` REUSE CONTRACT
(line 28): `"Scoring: tempo_accuracy.octave_eval … + TOL + OCTAVES + BPM_LO/BPM_HI in-range gate."`.
The sweep **imports** these constants directly from `tempo_accuracy`.

**Verdict on in-range filter: IDENTICAL.**

### 2.3 Acc1 definition

`tempo_accuracy.py` `octave_eval`: `acc1 = abs(det - gt) / gt <= TOL`. The `TOL` constant is a
relative tolerance (MIREX-style, ±4% by convention). The sweep imports and uses the identical
`octave_eval` function and `TOL`.

**Verdict on Acc1: IDENTICAL.**

### 2.4 Acc2 definition and octave-forgiveness set

`tempo_accuracy.py` `octave_eval`:
```python
errs = [(abs(det - k * gt) / (k * gt), k) for k in OCTAVES]
best_err, best_k = min(errs)
return bool(acc1), bool(best_err <= TOL), best_k, best_err
```
`OCTAVES = {1/3, 1/2, 1, 2, 3}` — five relations: sub-third, half, unison, double, triple.

The sweep imports `octave_eval`, `TOL`, and `OCTAVES` directly. The forgiveness set is identical in
both scripts by import, not by coincidence.

**Conformance to HarmonixSet / MIREX convention:** MIREX standard Acc2 uses `{1/2, 1, 2}`. The
scripts' set `{1/3, 1/2, 1, 2, 3}` is **wider** than standard, adding x1/3 and x3 forgiveness.
This inflates Acc2 relative to published HarmonixSet benchmarks. Both numbers are inflated equally,
so the _gap_ is unaffected by this choice, but absolute figures cannot be compared to literature
without qualification.

**Verdict on Acc2 forgiveness: IDENTICAL between the two scripts. Non-standard (wider than MIREX).**

### 2.5 BPM extraction — the critical asymmetry

This is where the scripts diverge fundamentally.

**`tempo_accuracy.py` (`detected_bpm`):**
```python
# Last 50% of clip, take the MODE of the integer-rounded BPM trajectory
mode_bpm = Counter(np.round(b).astype(int).tolist()).most_common(1)[0][0]
```
The detected BPM is the **steady-state modal output of the real `sb_tempo` winner-selection loop**,
running the full Goertzel resonator bank → `sb_sel_score` → hysteresis → winner-bin centre. This is
a firmware causal time-series. The BPM grid is integer 60–155, 1 BPM resolution.

**`acf_ceiling_sweep.py` (the 53.1% config):**
The sweep scores the `ac_ceiling_bpm()` function (copied from `tempo_accuracy.ac_ceiling_bpm`):
```python
# Mean-subtract novelty, full ACF, zero lag0, argmax inside lag window, BPM = 60*fps/lag
lag = lo + int(np.argmax(ac[lo:hi]))
return 60.0 * fps / lag
```
With parabolic interpolation (the config that achieves the 53% ceiling, per `sb_tempo.cpp` line 98
comment and the sweep's knob B), the detected BPM is a **single-shot global ACF argmax on the
whole-clip novelty**, not a causal frame-by-frame tracker. This is the _theoretical ceiling_ for
what any causal tracker could achieve if it had the same novelty as input.

**This is a different detector scored the same way.** The 53.1% is the score for a non-causal,
whole-clip ACF oracle. The 40.6% is the score for the causal sb_tempo winner-selection loop.
They are not the same estimator.

### 2.6 Quantisation / BPM grid comparability

- Firmware: integer 60–155 BPM, 1 BPM steps.
- ACF ceiling (integer argmax, no parabolic): BPM = `60 * fps / lag` — discrete but
  non-uniform (larger quantisation error at high BPM). At 44.44 Hz, ±1 lag ≈ ±13 BPM near
  174 BPM (sweep preamble, line 15–16).
- ACF ceiling (with parabolic): continuous sub-lag interpolation, finer effective resolution.

The parabolic config (the one cited as 53%) has _higher_ BPM resolution than the integer-mode
firmware output. This is a secondary advantage the firmware detector cannot directly replicate.

---

## 3. Are the two numbers apples-to-apples?

**No.** The scoring infrastructure (GT, corpus, TOL, OCTAVES, in-range filter, `octave_eval`) is
byte-for-byte identical. The asymmetry is in what is being scored:

| Dimension | `tempo_accuracy.py` (40.6%) | `acf_ceiling_sweep.py` (53.1%) |
|---|---|---|
| Detector | sb_tempo causal firmware loop (winner-selection) | Non-causal whole-clip ACF oracle |
| BPM source | Modal winner-bin, last 50% of trajectory | Single ACF argmax (+ parabolic interp) |
| Causality | Causal, online | Acausal, offline global |
| Purpose stated | Firmware Acc2 score | Theoretical ceiling for winner-selection |
| Comparison validity | Firmware score | Upper bound only |

The 12pp "gap" is therefore the distance between the firmware's causal tracker and its own
acausal ceiling on the same input, not a gap between two detectors scoring identically.
The sweep explicitly labels this as a ceiling (its own docstring: "the CEILING the detector's
winner-selection should reach"). The claim that these are "scored the SAME way" is _true of the
scoring function_ but ignores that the detectors are architecturally different.

---

## 4. Is the gap real?

**Yes, the gap is real** — the firmware's winner-selection underperforms the ACF ceiling by ~12pp
in-range Acc2. The ceiling is achievable in principle (it is derived from the same novelty the
firmware receives). The gap is a valid optimisation target.

**But the framing "close the gap between 53.1 and 40.6" is misleading.** The 53.1% ceiling is
only achievable with non-causal access to the entire clip and parabolic sub-lag interpolation.
A causal firmware ACF (44.44 Hz, real-time) at integer lags scores lower than 53.1% — the sweep
was designed specifically to measure _how much lower_ (the risk it de-risks). The sweep's own
preamble warns: "The ~50% Acc2 'ceiling' quoted from host work was measured at 133.33 Hz on host
novelty — UNVERIFIED at firmware conditions."

The committed firmware already includes `sb_compute_acf_salience` with parabolic interpolation
(see `sb_tempo.cpp` lines 228–278), and the comment at line 98 reads: "3-point parabolic sub-lag
interpolation restores the 53% ceiling." If this is accurate, the firmware's _current_ Acc2 of
40.6% post-integration already accounts for the ACF term — meaning the 40.6% is _with_ ACF, and
the remaining gap is not the ACF ceiling gap at all but something else (winner-selection logic,
quartic weighting, low-bin pinning).

---

## 5. Sanity-check: Acc2 inflation vs HarmonixSet convention

Standard MIREX/HarmonixSet Acc2 uses `{1/2, 1, 2}`. Both scripts use `{1/3, 1/2, 1, 2, 3}`.
Adding x1/3 and x3 forgiveness will inflate Acc2 by a few percentage points above published
benchmarks. The absolute numbers (53.1%, 40.6%) therefore cannot be directly compared to
published results without a correction note. The gap (12pp) is immune to this since both are
equally inflated.

---

## 6. Verdict

**NOT-COMPARABLE** — the scoring _function_ (GT, TOL, OCTAVES, in-range gate, `octave_eval`) is
identical, but the _detectors_ being scored are architecturally different: firmware causal tracker
vs. non-causal whole-clip ACF oracle. The 53.1% is a ceiling, not a peer score.

The 12pp gap is real and the plan direction is correct, but it must be framed as "firmware is 12pp
below its own ACF ceiling" — not as "two comparable detectors scored identically with a gap to
close," because the ceiling is by definition unreachable by a causal online system without
significant lag.

**Confidence: HIGH.** The REUSE CONTRACT in `acf_ceiling_sweep.py` (lines 20–30) is explicit that
scoring is identical; the asymmetry is entirely in what `detected_bpm` vs `ac_ceiling_bpm` return.
No empirical cross-run needed — the code makes the distinction unambiguous.
