## C1b — ACF ceiling at ~53% Acc2 (44.44 Hz, parabolic, raw novelty)

**Verdict: REFUTED — the prior claim is wrong on the best config**

Live sweep (`scripts/regression-harness/acf_ceiling_sweep.py`) run from clean tree, 36-track HarmonixSet corpus, 8 configs:

| config | Acc1 | Acc2 | octErr |
|---|---|---|---|
| 133.33Hz / int / raw | 21.9% | 53.1% | 0.085 |
| 133.33Hz / int / log1p | 25.0% | **56.2%** | 0.083 |
| 133.33Hz / parab / raw | 21.9% | **56.2%** | 0.083 |
| 133.33Hz / parab / log1p | 25.0% | **56.2%** | 0.081 |
| 44.44Hz / int / raw | 12.5% | 46.9% | 0.090 |
| 44.44Hz / int / log1p | 15.6% | 43.8% | 0.091 |
| **44.44Hz / parab / raw** | 12.5% | **53.1%** | 0.083 |
| 44.44Hz / parab / log1p | 15.6% | 50.0% | 0.086 |

BEST overall: **133.33Hz / int / log1p — Acc2 56.2%**, not 53%.
The 53.1% figure applies only to the `44.44Hz / parab / raw` row, which is NOT the best config. The best config is 133.33 Hz (full AP rate), not the firmware-native decimated rate. The prior claim "53% ceiling at 44.44 Hz, parabolic, raw novelty" is stable and reproducible for that specific config, but is not the ceiling — it is the firmware-rate ceiling.  The true host ceiling is 56.2% Acc2 (133.33 Hz / log1p). The 53.1% figure is not a fluke (three 133.33 Hz configs produce ≥56.2%; the 44.44 Hz parab/raw row is consistent across runs), but the description of it as "the ACF host ceiling" is wrong — it is the firmware-rate sub-ceiling.

Corpus: 36 tracks, 32 in-range (60–155 BPM). Scoring reuses `tempo_accuracy.octave_eval` exactly; numbers are directly comparable to the committed baseline (Acc2 28.1%).

## C2b — v3 donor has NO ACF, NO tempo prior, NO octave arbiter

**Verdict: REFUTED — v3 has an octave arbiter; the ACF/prior absence is VERIFIED**

Grep of `/Lightwave-Ledstrip/firmware-v3/src/` (excluding `.pio/`, `.venv/`, `.cache/`) for `acf|autocorr|autocorrelat` in all `.cpp`/`.h` files: **zero hits in firmware source**. The only matches were in chardet/pygments third-party Python packages — irrelevant. No ACF in the v3 donor.

Grep for `prior|gaussian` in v3 tempo source: only FastLED noise examples (`octaves=1`) and FastLED test gaussian comments — none in audio/tempo code. No tempo prior in the v3 donor.

However, `vendor/tempo.h` implements `esv11_pick_top_tempo_bin_octave_aware()` — a full **octave arbiter** with half-time and double-time correction logic:
- **Double-time arbiter**: promotes the double-BPM bin when raw winner is <80 BPM and confidence >0.06, with persistence gate (50 consecutive frames) and magnitude-ratio threshold (0.56–0.72×).
- **Half-time arbiter**: promotes the half-BPM bin when raw winner ≥132 BPM and the half-magnitude ≥0.92× of selected score.
- **Edge rebound**: recovers 78–84 BPM tactus when raw winner is pinned ≥138 BPM with low confidence.
- **210-BPM alias rescue**: redirects 128–136 BPM surrogate to 102–108 BPM tactus.

This function is called from `EsV11Backend.cpp:231` in production. The claim "v3 has NO octave arbiter" is **REFUTED**. The arbiter is implemented, called, and non-trivial. There is no ACF or Gaussian prior, but there is a full half/double magnitude-ratio arbiter.

## C2d — octave arbiter (Stage B / task #6) is specced-but-UNIMPLEMENTED in the fork

**Verdict: REFUTED — the fork has a partial octave defence already implemented**

Grep of `SPECTRASYNQ_K1_FIRMWARE/audio/sb_tempo.cpp` for `half.*tempo|double.*tempo|octave|arbiter|half.*beat|double.*beat|half.*hz|double.*hz`:

- Line 48: `// Log-Gaussian tactus prior (winner SELECTION only — Step 2 octave defence)`
- Line 52: reference to "LOW-BIN PINNING" as the dominant failure mode
- Line 61: `//      Symmetric in log2 -> half and double penalised equally; broad (SIGMA octaves)`
- Line 65: `static const float SB_TACTUS_SIGMA = 0.9f;   // octaves`
- Line 206: Acc2 improvement commentary referencing `tempo-octave-baseline.md`

The **log-Gaussian tactus prior** (`sb_tempo_prior[SB_NUM_TEMPI]`, centred at 120 BPM, σ=0.9 octaves) is declared as a static array and described as a live octave-defence mechanism used in `sb_update_winner` only. This is not a stub — the prior array, its constants, and the `sb_compute_acf_salience()` function (parabolic sub-lag ACF, 50+ lines of live code) are all present and wired into the winner-selection path per the in-file comments.

The fork does NOT reproduce the v3 `esv11_pick_top_tempo_bin_octave_aware()` magnitude-ratio half/double test — that specific mechanism is absent. But a different octave-defence mechanism (log-Gaussian prior + ACF salience) is actively implemented. The claim "octave arbiter is specced-but-UNIMPLEMENTED" is **REFUTED**; the arbiter is implemented using a different architecture than the v3 donor.
