# Firmware change requests from K1-FE-SHOW-M1 (revision 2, 10 Nov 2026)

Resident build examined: `ed0aa984` (`k1_fe_bench_b489`, bench K1 B489A500); the PRSM/authored source files are byte-identical to `407fdf6f`. Revision 1 (9 Nov) proposed small patches; the review showed several were too narrow. This revision states requirements and completion conditions; the smallest implementation is the FW lead's call.

**FE lane moved on (checked 10 Nov 15:50 AWST): `lane/k1-fe-release` is now `8b202f46` (rc2 receipt).** Between `407fdf6f` and `8b202f46`: `k1_prsm.*`, `k1_authored_source.*` and the `check_serial` scanner/hotkey routing are unchanged, so items 1–4 below remain open and Lane B's byte-safety oracle still applies. `e28dd927` ("validate serial input before commit") validates typed `:` setter values and moves noise-calibration reset to the audio core — it does NOT stop stream bytes reaching single-byte hotkeys (item 1). `c44172fa` retargets `k1_fe` at K1-FE-Gx and blocks `k1_fe` from every unit, including the Main RPL, until a Gx MAC is registered. The FE lane's `K1_MAIN_RPL_PINMAP_V1` still selects LED pins 15/16/17/18; the Main RPL rewire (2/3/5/6) exists only on local `wip/rpl-pins-20261110` (`2a620f7e`), so an FE-lane Main RPL build flashed as-is would leave the rewired plate dark. The FW lead's receipt (`docs/handover/RECEIPT-FE-FW-2026-11-10.md`, finding 4) flags the same merge hazard.

**Bench test target from 10 Nov 2026 (unit swap):** the bench K1 is now the Main RPL, chip `9087A500`, USB `B4:3A:45:A5:87:90`, read back running `k1_main_rpl_im69d` @ `2a620f7e` (local branch `wip/rpl-pins-20261110` = `68a684dc` + LED data on GPIO 2/3 (primary) and 5/6 (secondary); microphone DATA 8 / CLK 9 unchanged), build stamp `1794248403`, WS2816 dual-DIN, dual IM69D130. Its prepared-stream receiver is the same as `407fdf6f` (the `serial_menu.cpp` difference is emulator-only hooks). Candidate builds for this unit must carry this unit's pin map — pin maps are per-build references, not locks (Captain, 10 Nov). Today `K1_MAIN_RPL_PINMAP_V1` both selects this unit's map and is inherited by `k1_fe`; select the map per target board rather than through that shared flag. The resident build has no LED capture: a capture build (render trace, both edges if available) with this pin map is needed for the bench rerun, and flashing it needs the Captain's go. Recovery material for the previous image (`68a684dc`) exists: the flashing session matched a read-back to a clean build except 45 build-stamp bytes (registry changelog, 10 Nov). The old bench unit B489A500 results remain valid for that unit only.

Executable acceptance tests: emulator gates in `_scratch/k1-fe-show-m2_20261110/m2-emu/gates.py` (built by lane m2-emu; `--src <candidate firmware export>`), plus the source-level oracles in `lane-b/oracle/`. The emulator captures the WS2816 output path; the bench B489 drives WS2812 — emulator bytes and bench bytes are NOT interchangeable native-output evidence.

| **2 — with it** | **Deterministic colour start.** Prepared playback starts from a show-defined palette and phase, not whatever live listening left behind, and keeps the effect's existing energy-driven colour response inside the approved palette. **Diagnose first:** revision 1 called the result "flat palette-only colour", but `lane-a/CR-A7-wfhyb-authored-drive.md:13–16, 22–25` says the effect already has an energy-driven colour walk that authored pressure should drive once live dependencies are removed.
